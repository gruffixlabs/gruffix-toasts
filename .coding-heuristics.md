# Coding Heuristics

These are guidelines. Exceeding a size or complexity guideline is a signal to reconsider the structure or explain the tradeoff in the pull request. Do not split cohesive code or introduce types solely to meet a threshold.

## Design

- Prefer the simplest thing that works. No layers or generic code “for later.” Introduce protocols for a concrete need, such as testing or isolating a system boundary, not a hypothetical future implementation.
- Extract small, reusable pieces when a pattern appears a second time. If you're about to write something similar to existing code, extend or extract from that code instead of adding a parallel bespoke version. The “for later” rule targets speculative layers and protocols, not sensible generalization. When you choose bespoke code over extraction, say so and why in the handoff.
- Value types first. Use classes when reference semantics, lifecycle or framework requirements justify them.
- Use typed throws where they help callers. Never swallow errors with an empty `catch` or a careless `try?`. Intentionally ignoring an error should have a clear reason.
- Pass dependencies in rather than using globals.
- Follow the Swift API Design Guidelines, subject to the naming exceptions below.
- Implementation comments explain why. Documentation comments describe behavior, inputs, outputs and important constraints where useful. Avoid comments that merely repeat the code.
- No commented-out code.

## Concurrency

- **Use the language mode and concurrency checking set in the root `AGENTS.md` Project baseline.** Fix isolation and sendability issues rather than suppressing diagnostics or weakening compiler checks.
- **Prefer compiler-checked concurrency.** Use actors for shared mutable state and `@MainActor` for UI-isolated state. Prefer immutable, `Sendable` values across isolation boundaries.
- **Avoid manual synchronization and concurrency escape hatches.** Do not introduce `NSLock`, other lock-based synchronization, `@unchecked Sendable`, `nonisolated(unsafe)` or `@preconcurrency` workarounds without asking. If a framework boundary appears to require one, explain why a compiler-checked approach is insufficient and propose the smallest exception.
- **Keep concurrency proportional to the task.** Don’t introduce actors or asynchronous work where ordinary synchronous code is sufficient.

## Structure and Size

- **Organize by feature, then by kind of file.** Create only the subfolders a feature needs. This is an example, not a required architecture:
  ```
  Leaderboard/
    Views/
    Components/
    ViewModels/
    Modifiers/
  ```
- **In a Swift package,** feature folders live under `Sources/<Target>/`, and tests mirror that structure under `Tests/<Target>Tests/`.
- **Consider splitting directories once they exceed about 10 immediate entries.** Group by a meaningful responsibility; don’t add folders merely to reduce the count.
- **Favor small, composable components and modifiers.** Build screens from small views that add value.
- **Aim for files under about 300 lines.** Past about 400, look for distinct responsibilities to extract. Use extensions only as described below.
- **Aim for functions and view bodies up to about 60 lines, most much shorter.** Give each one job. Prefer no more than about 3 levels of nesting; use `guard` and early returns where they improve clarity.
- **Aim for about 4 parameters or fewer.** Beyond that, consider whether related values form a meaningful type. Don’t introduce a parameter wrapper solely to reduce the count.
- **Keep control flow easy to follow.** Simplify deeply nested or interacting conditions. Don’t extract helpers merely to reduce a complexity score.

## Files and Extensions

- **One main type per file.** Small supporting types, such as error enums and simple enums, may stay with the type they support.
- A type’s own small members, such as an enum’s computed properties, live in its declaration rather than a separate extension file.
- For enums used only within a single type, consider declaring them within that type.
- **Use extensions only when they add meaning:**
  - Complex protocol or delegate conformances.
  - Functionality tied to a specific technology, kept apart from the core type, such as a SwiftUI convenience on a SwiftData model:
    ```swift
    // Person+SwiftUI.swift (app target)
    extension Person {
        convenience init(_ name: String, color: Color) {
            self.init(name, color: CodableColor(from: color))
        }
    }
    ```
    The model stores `CodableColor`; the extension converts the SwiftUI value at the boundary.
- **Name extension files `Type+Concern.swift`,** where the concern is the conformance or technology, such as `Person+SwiftUI.swift` or `GameView+UITextFieldDelegate.swift`.

## Member Order Within a Type

1. Stored properties.
2. Computed properties, after the stored properties or next to the stored property they’re derived from.
3. Initializers (`init`).
4. Deinitializer (`deinit`).
5. Methods.

Within each group, order declarations by logical flow, keeping related ones together. Access level doesn’t affect order.

**Exception:** a SwiftUI `body` and other view-builder properties go after the initializers, with the methods. They act as functions.

## Naming

- **Types are nouns:** structs, classes, actors and enums, such as `Player`, `ScoreEntry` and `EventDetector`.
- **Functions with side effects use verbs**, such as `recordEntry(_:)`.
- **Functions without side effects describe the result or transformation**, such as `player(named:)`, `standings(after:)` and `sorted()`. Follow Swift conventions for mutating and nonmutating pairs, such as `sort()` / `sorted()`.
- **Protocols** are nouns when they describe what something is (`ScoreSource`), and end in `-able` or `-ible` when they describe a capability (`Shareable`, `Undoable`). Never use `-ing` for new protocol names.
- **Booleans read as assertions:** use `is`, `has` or `can`, plus `show` for presentation state, such as `isComplete`, `hasPermission`, `canUndo` and `showPlayerEditor`.
- **Acronyms are cased like words:** `deviceId`, `jsonData`, `dueDateAsap` and `FooBarDna`, rather than `deviceID`, `dueDateASAP` or `FooBarDNA`. This is a deliberate exception to the Swift API Design Guidelines.
- Preserve the spelling of framework-provided names and names required by protocol conformances, including `UUID` and `URL`.

## Previews

- **View files have one default `#Preview`** for quick testing in the canvas. Wrap previews in `#if DEBUG` / `#endif`.
- **Variations and multiple states go in `ViewName+Previews.swift`** next to the view once more than the default is needed. Wrap the entire file in `#if DEBUG` / `#endif`.
- **Shared fixtures**, including `PreviewModifier`s and sample data, live in the target's `Demo/` folder. Swift packages have no `Preview Content` folder or Development Assets, so wrap each fixture file in `#if DEBUG` / `#endif` to keep it out of release builds.
- Preview requirements do not authorize builds, screenshots or automated verification.
